- Set `vulpea-db-async-extraction` to `full` in `lisp/init-local-vulpea.el`, so a save no longer freezes Emacs while the note is re-indexed. Nothing runs on `before-save-hook`; autosync watches the directory with filenotify, and a save enqueues the file for `vulpea-db-sync--process-queue`, which with the nil default read, hashed, parsed and wrote it on the main thread — and with `vulpea-db-parse-method` at its `temp-buffer` default, re-ran `org-mode` per file to do it. Windows pays the worst for that, between slower file I/O and a heavier `org-mode` startup. `full` hands the work to a persistent `emacs --batch` worker that also writes the results through its own connection, leaving the main thread only the org-id registration, so the one cost Windows is genuinely bad at — spawning the subprocess — is paid once per session rather than once per save. Two consequences: the database switches to WAL journaling, which rules out putting `vulpea-db-location` on a network share (it stays under `user-emacs-directory`), and the worker skips `org-mode-hook` like `single-temp-buffer` does, reading org settings from its own mirrored allowlist instead. `vulpea-db-sync-external-method` stays nil, which is also the right setting for Windows: `auto` finds no fswatch there and falls back to polling the whole tree every two seconds.
